Homework 2: Ethereum Wallet Pipeline & Primitives

Detailed breakdown of key derivation, asymmetric cryptography, hashing, and checksums

1. Comprehensive Wallet Derivation Pipeline

1. Mnemonic Sentence & Seed Generation (BIP-39)

Computers generate a cryptographically secure random number (128 to 256 bits of raw entropy). To make this user-friendly, a short SHA-256 checksum is appended, and the sequence is split into 11-bit chunks. Each chunk corresponds to a specific word in a standardized 2,048-word dictionary, forming a 12-to-24 word mnemonic phrase.

To obtain a usable cryptographic key, the mnemonic (along with an optional passphrase) is stretched using the PBKDF2 algorithm with 2,040 iterations of HMAC-SHA512. This computationally intensive process outputs a deterministic 512-bit Master Seed, making brute-force attacks significantly harder.

2. Hierarchical Deterministic Key Derivation (BIP-32 & BIP-44)

The 512-bit seed is split into a 256-bit Master Private Key and a 256-bit Chain Code. Under BIP-32, the chain code acts as extra entropy allowing parent keys to deterministically generate an infinite tree of child keypairs without exposing the master key.

BIP-44 enforces a multi-level derivation path across wallets:
m / 44' / coin_type' / account' / change / address_index
For Ethereum, coin_type is registered as 60'. The default single-account path m/44'/60'/0'/0/0 guarantees that any wallet software (e.g., MetaMask, Rabby, Exodus) deriving keys from the same seed will always recover the exact same Ethereum addresses.

3. Elliptic Curve Public Key Generation (secp256k1)

The derived child key is a 256-bit scalar integer (the Private Key k). To generate the Public Key Q, the private key undergoes scalar point multiplication with the fixed generator point G on the secp256k1 curve (y² = x³ + 7 mod p):
Q = k · G = (x, y)

The resulting uncompressed public key consists of two 256-bit (32-byte) coordinates concatenated together (x || y), yielding a 64-byte payload (often prefixed with 0x04 to signal uncompressed format).

4. Address Hashing (Keccak-256)

The 64-byte uncompressed public key (excluding the 0x04 prefix) is passed into the Keccak-256 hash function, returning a 32-byte digest. To keep account identifiers compact on-chain, Ethereum truncates this hash: the last 20 bytes (160 bits) are kept to form the raw Ethereum address.

5. Checksum Encoding (EIP-55)

Raw Ethereum hex addresses are entirely lowercase and contain no built-in error detection. EIP-55 introduces a backward-compatible checksum by capitalizing specific hexadecimal letters based on the Keccak-256 hash of the lowercase address string. If the $i$-th character's corresponding hash nibble is $\ge 8$, that letter is capitalized; otherwise, it stays lowercase. A typing mistake alters the hash, causing the checksum verification to fail immediately.

2. Categorization of Cryptographic Concepts

Category Primitives / Standards Core Role & Guarantee
Key Generation & Derivation BIP-39, BIP-32, BIP-44, PBKDF2 Translates human-rememberable words into a deterministic, infinite tree of accounts without storing individual keys.
Public-Key Cryptography secp256k1 (ECDSA) Provides a trapdoor function ($k \to Q$) allowing transaction signing and ownership verification without revealing the private key.
Hashing Keccak-256 Compresses a 64-byte public key to a 32-byte output; destroys structure to prevent reverse algebraic mapping.
Checksum & Encoding EIP-55, Hex (Base16) Adds zero-overhead typo detection and converts raw binary key arrays into human-readable strings.

3. Historical Chronology & Evolution

  • 1977 — RSA: The pioneering asymmetric public-key cryptosystem based on prime factorization.
  • 2001 — SHA-2 (SHA-512): Standardized by NIST based on the Merkle-Damgård construction.
  • 2012 — BIP-32: Introduced Hierarchical Deterministic (HD) wallets to simplify key management in Bitcoin.
  • 2013 — BIP-39: Standardized mnemonic seed phrases for human-friendly wallet backups.
  • 2014 — BIP-44: Standardized multi-account, multi-coin derivation paths.
  • 2015 — SHA-3 (NIST FIPS 202): NIST formally finalized SHA-3 based on the Keccak sponge algorithm.
  • 2016 — EIP-55: Vitalik Buterin introduced mixed-case checksum encoding for Ethereum addresses.

4. Critical Differences & Technical Questions

Keccak-256 vs. Standardized SHA3-256

Although SHA-3 is derived from Keccak, Keccak-256 is not identical to SHA3-256. Ethereum adopted the original Keccak implementation in 2014, months before NIST published the official FIPS 202 SHA-3 standard in August 2015.

During finalization, NIST added a 2-bit domain separation padding rule (appending 0x06) to distinguish different SHA-3 variants. The original Keccak algorithm used padding starting with 0x01. Because the underlying message padding is different, hashing the exact same string with Keccak-256 and SHA3-256 results in two completely different output hashes. Ethereum kept original Keccak-256 to maintain EVM opcode backward compatibility.

Why use multiple distinct algorithms instead of one single primitive?

A single cryptographic primitive cannot simultaneously satisfy security, usability, efficiency, and safety requirements across a blockchain stack:

  • BIP-39/32/44 solve Key Management: Raw 256-bit numbers cannot be easily memorized or backed up by humans. HD standards bridge human memory (12 words) to structured tree derivations.
  • secp256k1 solves Identity & Authorization: Public-key math allows users to sign transactions off-chain and prove ownership on-chain without revealing private keys.
  • Keccak-256 solves Storage & Privacy: Public keys are 64 bytes. Hashing and truncating them to 20-byte addresses reduces state storage costs on the EVM and adds a layer of privacy (the public key is hidden until an outbound transaction is sent).
  • EIP-55 solves Operational Safety: Prevents catastrophic user typos when pasting addresses, without requiring extra bytes or changing the address length.
